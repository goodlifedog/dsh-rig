# 外部评审：项目有没有跑偏 + 漏洞清单

> 评审时间：2026-11-07 · 基于当前工作区实际状态（git log、测试、代码抽查）
> 评审方式：只读检查 + 命令验证，不改代码

## 一、先给结论

**工程卫生很好，但定位在漂移。**

- 好的部分：295 个测试全过（294 pass / 1 skip）、无 TODO/FIXME、无明文密钥、无硬编码用户路径、Windows 声明有诚实标注。
- 风险的部分：最近提交的重心从「可观测的后台控制」转向「通用多通道自动化框架」。

证据（最近 8 条提交）：

```
cd09cda AppleScript 通道落地
b481bd8 CDP 通道落地：第三方 Chromium 应用可直连页面驱动
5dfae86 支持方式改为按运行时族设计，不再逐个应用适配
f39f73c 清点报告加状态与建议控法的一致性校验
```

新增/改造的模块：`app-profile` `app-inventory` `app-presets` `app-runtime` `app-strategy` `app-window-ready` `driver-resolution` `applescript-driver` `cdp-driver`，以及 12+ 个新任务脚本。

## 二、跑偏判断：是，轻微跑偏

**原来的定位**：给 computer-use 加「可观测 + 可验证」的那一层。差异化在小窗和验收。

**现在的走向**：在做「多通道控制框架」（AX / CDP / AppleScript / visual）。

问题在于：

1. **AX 和 CDP 这两条通道 ocu 已经做了**，重复建设，而且我们做得不如它稳。
2. **每加一个 driver，维护面翻倍**：4 条通道 × N 个应用 × 2 个平台。
3. **护城河被稀释**：别人记住的不再是「有窗口能看见」，而是「又一个自动化框架」。

**建议**：driver 层只做「够用」，把省下来的精力砸在验证层和小窗上——那才是别人没有的。

判断标准一句话：**新功能如果不能增强「看得见」或「验得准」，就不该做。**

## 三、漏洞清单

### P0（必须处理）

**1. 新通道没有进验收**
- `core/acceptance.mjs` 只跑 6 个老任务：boss-scan / multi-app / form-fill / platform-demo / browser-demo / electron-demo
- 新增的 `applescript-channel`、`cdp-channel`、`app-matrix`、`background-control` **都没进验收**
- 后果：新代码没有出口把关，等于「写完就算完成」
- 修法：把新通道任务加进 acceptance，`npm run accept` 不通过就不算完成

**2. 工作区有 5 个未提交改动**
- `core/app-profile.mjs`（111 行）、`core/driver-resolution.mjs`（158 行）、`scripts/app-resolve.mjs`（145 行）都是未跟踪文件
- 后果：一次误操作就可能丢 400 多行工作
- 修法：先提交，再继续

**3. AppleScript 通道可能违反核心卖点**
- 核心承诺是「不抢焦点、不动你的窗口」
- AppleScript 操作应用时通常会 `activate`，那就会抢前台
- 现状：我没在 `core/applescript-driver.mjs` 里找到 activate 字样，但也没找到证据证明它不抢
- 修法：实测一次，记录「操作前后前台应用是否变化」，把结论写进能力矩阵；如果有激活行为，要么标注「会短暂夺焦」，要么不做这条通道

### P1（建议处理）

**4. 两套定位表述自相矛盾**
- README 第 7 行说「一个自用的 macOS 桌面自动化框架」
- 第 133 行又说「本项目真正的价值在小窗回显、后台调度、可验证」
- 修法：统一成后者。框架是手段，可观测才是卖点

**5. 文档入口缺失**
- `flow/` 现在有 20+ 份文档，第一次来的人不知道该读哪份
- 修法：加一份 `flow/INDEX.md`，按「想做什么」组织，最多 10 条

**6. visual 兜底与设计原则冲突**
- `driver-resolution` 里保留了 `visual`（抓画面 + 坐标点击）作为兜底
- 但架构文档第 2 条原则写的是「不依赖截图猜坐标」
- 修法：要么删掉 visual，要么明确写「仅诊断用，不参与自动执行」

**7. Windows 声明仍在能力矩阵里**
- 虽然标了「未实机验证」，但 README 第 52 行仍写「macOS launchd / Windows 计划任务」
- 修法：能力矩阵里把 Windows 整列标灰或移除，等真机验证后再加回

### P2（可以放后面）

**8. 测试结构偏单元**
- 295 个测试 3.5 秒跑完，说明几乎全是纯函数；e2e 只有 acceptance 那 6 条
- 修法：给每条 driver 至少一条 e2e

**9. 任务脚本没有分类**
- `core/tasks/` 里 25+ 个文件，业务任务、探针、演示混在一起
- 修法：分 `tasks/business/` `tasks/probe/` `tasks/demo/` 三个目录

**10. 缺统一校验入口**
- 现在有 `check`、`test`、`accept`、`repo:check`、`restart:check`
- 修法：加一个 `npm run verify` 把它们串起来，一条命令判断「能不能发版」

## 四、给会话的一句话建议

> 别再往「支持更多应用」上加功能了。把现有通道的**验收**补齐、把**定位**统一、把**未提交的代码**先提交，比再加一个 driver 有价值得多。

### 新发现的实质漏洞

**P1：`pidMatchesProcess` 会把 Helper 进程认成主应用（实测）**

```
pidMatchesProcess('Google Chrome Helper', 'Google Chrome')  ->  true   ← 错
```

原因在匹配规则里的 `base.startsWith(want + ' ')`。

影响：安全层的本意是防「pid 被系统复用后杀错进程」，但这条规则反过来让「Chrome Helper」被当成「Chrome」。
在按 pid 杀进程、或判断应用是否还在运行时，会误判。
`app-window-ready` 那条 `still-running` 变成 `pid-mismatch` 的测试失败，很可能就是这个规则改动引起的连带。

改法：要求 basename 精确相等；需要兼容路径形式时，只在最后一段做全等比较，不要用 startsWith 放宽。

**P2：`ensureHelper` 的 fail-closed 只查了文件与直接父目录**

- 目录链上的祖父目录没查（`/tmp` 这类世界可写路径下理论上可被替换）
- 现有文件不可信时注释写的是「编译覆盖」，但跨用户覆盖必然失败，且没有单独的失败分支说明

## 第十二轮复查（2026-11-08 01:15）

### 这轮挖到一个会让验收假绿的问题

`core/run-classify.mjs` 决定「哪些失败算环境问题、可以跳过」。它的规则太宽了。我写了个小测试喂了几个真实场景：

```
代码路径拼错 ENOENT   | failed=true envSkip=true | 环境缺少可执行文件
投递未送达            | failed=true envSkip=true | 投递未送达或已联系
锁屏                  | failed=true envSkip=true | 锁屏        ← 这条是对的
```

两条都有问题：

**① `/No such file or directory/` 太泛**
这条本来是为了认「机器上没装 node」，但它匹配的是 spawn 失败的通用信息——
**代码里任何一处路径写错，都会被当成「环境缺可执行文件」而跳过**，验收照样通过。

**② `/未送达/` 被归成环境跳过，方向彻底反了**
「未送达」正是我们花了好几个小时抓出来的假成功（弹窗说已发送、消息列表里没有）。
这是**功能失败**，不是环境不具备。把它归成跳过，等于验收亲手放过了这个 bug。

这解释了 CHANGELOG 里那句「验收从 11/12 恢复到全通过」——其中有几项可能不是修好了，是被归类跳过了。

### 建议这么改

1. ENOENT 规则收窄到明确特征：`env: node: No such file`，不要用泛化的 `No such file or directory`
2. 「未送达」移出环境规则，算真实失败；环境类只留「配额用尽 / 账号受限 / 锁屏」这类
3. 验收输出里**列出跳过项的名字**，并且跳过数超过阈值（比如 2 项）直接判不通过
4. 给 `run-classify` 补单测：拿真实失败样本喂进去，断言 `envSkip === false`

### 顺手审计了 overlay（结论是好的）

- 多会话有上限（12）、有 TTL 回收（30 分钟无活动自动关窗）
- 定时器成对管理，会话销毁时清掉 fade/idle/thumb
- 抓帧有 `!visible` 门控，窗口隐藏时不抓
- 静止画面会退避到 2fps，省 CPU；变化时能立刻跟上

这块没毛病，可以放心。

## 第十四轮复查（2026-11-08 01:25）

### 审计了重试策略：现在没踩到，但框架缺一块

`core/retry-policy.mjs` + `daemon.mjs` 的行为是：

- 临时性失败（Chrome 端口没起来、ECONNREFUSED、CDP 超时）→ 自动重跑
- **被超时终止（code=null）→ 也自动重跑**，理由是「外部卡住，再给一次机会」
- 环境类失败不重试（这条是对的）

风险在于：**重试是全局规则，不看任务有没有副作用。**
如果某个任务跑到一半已经点了「发送」或「提交」，然后被超时杀掉，重试就会**再发一次**。

好消息是现在没炸：
- `form-fill` 只填表不提交（我查了，没有提交/发送动作）
- `boss-greet` 有 `reports/greet-state.json` 记录已投 id，重跑会跳过

坏消息是框架层面**没有幂等声明**：我搜过 `idempotent` / `sideEffect` / `retryable`，一个都没有。
也就是说下一个写「点发送」任务的人，会默认继承自动重试，然后在某次超时后发两遍。

### 建议（低改动）

1. 任务注册表加一个字段：`sideEffects: true`（默认 false 表示只读/幂等）
2. `decideRetry` 收到 `sideEffects && code === null` 时**不重试**，直接报「可能已部分执行，需人工确认」
3. 副作用任务必须自己带幂等保护（像 boss-greet 的状态文件那样），并在任务头部注释写清楚

这轮和前几轮的状态完全一致（14 个脏文件、无新提交、daemon 未重启）。
主会话已经有一段时间没有产出，可能是卡住了或者在别的地方忙。
