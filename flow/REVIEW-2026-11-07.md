# 外部评审：项目有没有跑偏 + 漏洞清单

> 评审时间：2026-11-07 · 基于当前工作区实际状态（git log、测试、代码抽查）
> 评审方式：只读检查 + 命令验证，不改代码

## 一、先给结论

**工程卫生很好，但定位在漂移。**

- 好的部分：295 个测试全过（294 pass / 1 skip）、无 TODO/FIXME、无明文密钥、无硬编码用户路径、Windows 声明有诚实标注。
- 风险的部分：最近提交的重心从「可观测的后台控制」转向「通用多通道自动化框架」。

证据（最近 8 条提交）：

```
cd09cda AppleScript 通道落地
b481bd8 CDP 通道落地：第三方 Chromium 应用可直连页面驱动
5dfae86 支持方式改为按运行时族设计，不再逐个应用适配
f39f73c 清点报告加状态与建议控法的一致性校验
```

新增/改造的模块：`app-profile` `app-inventory` `app-presets` `app-runtime` `app-strategy` `app-window-ready` `driver-resolution` `applescript-driver` `cdp-driver`，以及 12+ 个新任务脚本。

## 二、跑偏判断：是，轻微跑偏

**原来的定位**：给 computer-use 加「可观测 + 可验证」的那一层。差异化在小窗和验收。

**现在的走向**：在做「多通道控制框架」（AX / CDP / AppleScript / visual）。

问题在于：

1. **AX 和 CDP 这两条通道 ocu 已经做了**，重复建设，而且我们做得不如它稳。
2. **每加一个 driver，维护面翻倍**：4 条通道 × N 个应用 × 2 个平台。
3. **护城河被稀释**：别人记住的不再是「有窗口能看见」，而是「又一个自动化框架」。

**建议**：driver 层只做「够用」，把省下来的精力砸在验证层和小窗上——那才是别人没有的。

判断标准一句话：**新功能如果不能增强「看得见」或「验得准」，就不该做。**

## 三、漏洞清单

### P0（必须处理）

**1. 新通道没有进验收**
- `core/acceptance.mjs` 只跑 6 个老任务：boss-scan / multi-app / form-fill / platform-demo / browser-demo / electron-demo
- 新增的 `applescript-channel`、`cdp-channel`、`app-matrix`、`background-control` **都没进验收**
- 后果：新代码没有出口把关，等于「写完就算完成」
- 修法：把新通道任务加进 acceptance，`npm run accept` 不通过就不算完成

**2. 工作区有 5 个未提交改动**
- `core/app-profile.mjs`（111 行）、`core/driver-resolution.mjs`（158 行）、`scripts/app-resolve.mjs`（145 行）都是未跟踪文件
- 后果：一次误操作就可能丢 400 多行工作
- 修法：先提交，再继续

**3. AppleScript 通道可能违反核心卖点**
- 核心承诺是「不抢焦点、不动你的窗口」
- AppleScript 操作应用时通常会 `activate`，那就会抢前台
- 现状：我没在 `core/applescript-driver.mjs` 里找到 activate 字样，但也没找到证据证明它不抢
- 修法：实测一次，记录「操作前后前台应用是否变化」，把结论写进能力矩阵；如果有激活行为，要么标注「会短暂夺焦」，要么不做这条通道

### P1（建议处理）

**4. 两套定位表述自相矛盾**
- README 第 7 行说「一个自用的 macOS 桌面自动化框架」
- 第 133 行又说「本项目真正的价值在小窗回显、后台调度、可验证」
- 修法：统一成后者。框架是手段，可观测才是卖点

**5. 文档入口缺失**
- `flow/` 现在有 20+ 份文档，第一次来的人不知道该读哪份
- 修法：加一份 `flow/INDEX.md`，按「想做什么」组织，最多 10 条

**6. visual 兜底与设计原则冲突**
- `driver-resolution` 里保留了 `visual`（抓画面 + 坐标点击）作为兜底
- 但架构文档第 2 条原则写的是「不依赖截图猜坐标」
- 修法：要么删掉 visual，要么明确写「仅诊断用，不参与自动执行」

**7. Windows 声明仍在能力矩阵里**
- 虽然标了「未实机验证」，但 README 第 52 行仍写「macOS launchd / Windows 计划任务」
- 修法：能力矩阵里把 Windows 整列标灰或移除，等真机验证后再加回

### P2（可以放后面）

**8. 测试结构偏单元**
- 295 个测试 3.5 秒跑完，说明几乎全是纯函数；e2e 只有 acceptance 那 6 条
- 修法：给每条 driver 至少一条 e2e

**9. 任务脚本没有分类**
- `core/tasks/` 里 25+ 个文件，业务任务、探针、演示混在一起
- 修法：分 `tasks/business/` `tasks/probe/` `tasks/demo/` 三个目录

**10. 缺统一校验入口**
- 现在有 `check`、`test`、`accept`、`repo:check`、`restart:check`
- 修法：加一个 `npm run verify` 把它们串起来，一条命令判断「能不能发版」

## 四、给会话的一句话建议

> 别再往「支持更多应用」上加功能了。把现有通道的**验收**补齐、把**定位**统一、把**未提交的代码**先提交，比再加一个 driver 有价值得多。

### 新发现的实质漏洞

**P1：`pidMatchesProcess` 会把 Helper 进程认成主应用（实测）**

```
pidMatchesProcess('Google Chrome Helper', 'Google Chrome')  ->  true   ← 错
```

原因在匹配规则里的 `base.startsWith(want + ' ')`。

影响：安全层的本意是防「pid 被系统复用后杀错进程」，但这条规则反过来让「Chrome Helper」被当成「Chrome」。
在按 pid 杀进程、或判断应用是否还在运行时，会误判。
`app-window-ready` 那条 `still-running` 变成 `pid-mismatch` 的测试失败，很可能就是这个规则改动引起的连带。

改法：要求 basename 精确相等；需要兼容路径形式时，只在最后一段做全等比较，不要用 startsWith 放宽。

**P2：`ensureHelper` 的 fail-closed 只查了文件与直接父目录**

- 目录链上的祖父目录没查（`/tmp` 这类世界可写路径下理论上可被替换）
- 现有文件不可信时注释写的是「编译覆盖」，但跨用户覆盖必然失败，且没有单独的失败分支说明

## 第十四轮复查（2026-11-08 01:25）

### 审计了重试策略：现在没踩到，但框架缺一块

`core/retry-policy.mjs` + `daemon.mjs` 的行为是：

- 临时性失败（Chrome 端口没起来、ECONNREFUSED、CDP 超时）→ 自动重跑
- **被超时终止（code=null）→ 也自动重跑**，理由是「外部卡住，再给一次机会」
- 环境类失败不重试（这条是对的）

风险在于：**重试是全局规则，不看任务有没有副作用。**
如果某个任务跑到一半已经点了「发送」或「提交」，然后被超时杀掉，重试就会**再发一次**。

好消息是现在没炸：
- `form-fill` 只填表不提交（我查了，没有提交/发送动作）
- `boss-greet` 有 `reports/greet-state.json` 记录已投 id，重跑会跳过

坏消息是框架层面**没有幂等声明**：我搜过 `idempotent` / `sideEffect` / `retryable`，一个都没有。
也就是说下一个写「点发送」任务的人，会默认继承自动重试，然后在某次超时后发两遍。

### 建议（低改动）

1. 任务注册表加一个字段：`sideEffects: true`（默认 false 表示只读/幂等）
2. `decideRetry` 收到 `sideEffects && code === null` 时**不重试**，直接报「可能已部分执行，需人工确认」
3. 副作用任务必须自己带幂等保护（像 boss-greet 的状态文件那样），并在任务头部注释写清楚

## 第十七轮复查（2026-11-08 00:30）

### 上轮的防呆建议，落地了

`daemon.mjs` 现在会捕获 EADDRINUSE，用 lsof 查出占用者 pid，打印「可能是手工启动的游离实例」，
然后以退出码 78 退出；`package.json` 也加了 `service:restart`。这条问题应该不会再复发。

### 新发现：进程收尾有三个缺口

**① daemon 收到 SIGTERM 直接 exit，不管正在跑的任务**
```js
process.on('SIGTERM', () => { server.close(); process.exit(0); });
```
现在 `service:restart` 会被频繁使用，每重启一次就可能留下一个**还在操作应用的孤儿任务进程**。

**② 超时只发 SIGTERM，没有 SIGKILL 兜底**
```js
const timer = setTimeout(() => { record(...); child.kill('SIGTERM'); }, timeoutMs);
```
任务卡在系统调用里会忽略 SIGTERM，`close` 事件永不到来 → promise 不 resolve → 队列卡死。

**③ 只杀直接子进程，孙进程会被孤儿化**
spawn 没开 `detached`，也没杀进程组。任务脚本拉起的 ocu / Chrome / Electron 都是孙进程，父进程一死它们继续跑。

### 现场证据（不是假设）

```
34619  ocu mcp               启动于 23:36:37（今天）
34620  OpenComputerUse        启动于 23:36:37
37097  OpenComputerUse        启动于 **11月6日 22:05:50** ← 已经活了 26 小时
48216  OpenComputerUse        启动于 23:57:40
```

三个 app-agent 挂在同一个 socket 上，其中一个是昨天的残留。

### 建议改法

1. `SIGTERM` 处理里：先 `process.kill(-pid, 'SIGTERM')` 杀当前任务进程组，最多等 5 秒，再 exit
2. runner 超时：SIGTERM 之后 5 秒补一发 SIGKILL
3. `spawn(..., { detached: true })`，然后用 `process.kill(-child.pid, sig)` 杀整组
4. daemon 启动时做一次残留清理：同一 socket 上活着的旧 app-agent，取最新一个保留，其余杀掉

问题在于这两条都**只凭一句自由文本**：

- 任何任务只要在失败输出里打一句「环境跳过」，验收就放过它（有意或无意都会发生）
- 「已恢复原值」这句本来是任务正常收尾的日志，出现在失败输出里却会被判成「页面结构已变」

### 建议：把「跳过」从关键词匹配改成结构化信号

现在判定靠正则猜日志。更稳的做法是让任务**显式声明**：

```json
{"event":"end","code":1,"envSkip":{"reason":"锁屏"}}
```

验收只信这个字段；自由文本匹配降级为「给人看的解释」，不参与 pass/fail。
这样任务想跳过必须自己声明原因，而且原因可以被统计和审计。

顺带两条小的：
1. 验收里跳过项超过 2 个直接判不通过（防止大面积跳过冒充通过）
2. 「已恢复原值」这条规则建议直接删掉——它描述的是任务动作，不是环境状态

## 第二十一轮复查（2026-11-08 01:05）

### 进程收尾改了大半，但漏了一层

他们按建议做了三件事：
- `runner` 里任务 `detached: true`，超时先 TERM 整组、5 秒后 KILL 整组（`killGroup`）
- `daemon` 收到 SIGTERM 时不再直接退出，先走 `shutdownWithRunningTask()`
- `daemon` 也 `detached: true` 起 runner，杀的时候用 `process.kill(-pid)`

看起来闭环了，但**进程组是两层，杀只杀了一层**：

```
daemon  ---spawn(detached:true)--->  runner（自成进程组 A）
                                       |
                                       +--spawn(detached:true)--> task（自成进程组 B，独立于 A）
                                                                     |
                                                                     +--> ocu / Chrome
```

`daemon` 杀的是 `-runnerPid`，也就是进程组 A。
但 task 因为 `detached: true` 已经跑到进程组 B 去了，**A 被杀不会波及 B**。

更直接的证据：`runner.mjs` 里**没有任何 `process.on('SIGTERM')` 处理**（我 grep 过，一条都没有）。
所以 daemon 重启时：runner 被 TERM 掉 → task 继续跑 → 它拉起的 ocu / Chrome 也继续跑。
这正是上一轮要解决的那个问题，只是换了一层。

### 修法（二选一）

**A. runner 转发信号（推荐）**
```js
let currentChild = null;
process.on('SIGTERM', () => {
  if (currentChild) { try { process.kill(-currentChild.pid, 'SIGTERM'); } catch {} }
  setTimeout(() => process.exit(0), 4000).unref();
});
```
daemon 杀 runner 的组 → runner 收到 TERM → 转发给自己的任务组。

**B. 任务不要 detach，跟 runner 同组**
这样 `-runnerPid` 一次就能覆盖 runner + task + 它们的孩子。
代价是 runner 自己也在组里，得用「先 TERM 组、runner 立刻 exit」的方式，稍麻烦。

### 附带一个小问题

`runner` 的 start 记录写的是 `pid: process.pid`（runner 自己），**没有记录任务子进程的 pid**。
出问题时想查「这个任务到底拉起了哪些进程」是查不到的。
建议 start 记录里同时带上 `taskPid`。

### 其他状态

README 仍未提 token（0 处）、仍无日志清理脚本。

### 但上一轮那个「组套组」的洞还在，而且 `/stop` 也一样

`runner.mjs` 里依然**没有 `process.on('SIGTERM')`**。也就是说：

| 路径 | 现在的行为 | 结果 |
| --- | --- | --- |
| daemon 重启 | 杀 runner 的进程组 A | task 在组 B，**continue 跑** |
| `/stop` 取消任务 | 只 `kill(pid)` 单个 runner | runner 立刻死，**task 组 B 完全没受影响** |

第二条更要紧：`/stop` 是用户日常操作。用户点了停，界面显示停了，
但真正在点鼠标、打字、开浏览器的那个进程还在跑。

代码证据：
```js
// /stop 路径（第 379 行）
try { process.kill(state.current.pid, 'SIGTERM'); } catch {}

// 关停路径（第 433-437 行）用的是 killGroup，两者不一致
```

### 一个改动同时解决两条路径

在 `runner.mjs` 加信号转发（模块级变量记住当前任务 child）：

```js
let currentChild = null;
function killTaskGroup(signal) {
  if (!currentChild) return;
  try { process.kill(-currentChild.pid, signal); } catch { try { currentChild.kill(signal); } catch {} }
}
process.on('SIGTERM', () => {
  killTaskGroup('SIGTERM');
  setTimeout(() => { killTaskGroup('SIGKILL'); process.exit(0); }, 4000).unref();
});
```

加了之后：daemon 重启杀组 A → runner 收到 TERM → 转发给组 B；`/stop` 杀 runner → 同样转发。

### 建议顺手加个回归测试

起一个假任务（spawn 一个 sleep 子进程），TERM 掉 runner，断言子进程也不在了。
这类「杀不干净」的问题，凭肉眼看代码很难发现，只能靠测试钉。

## 第二十五轮复查（2026-11-08 01:45）——应用锁会被「偷」

### 复现

`withAppLock` 用「锁文件 mtime 超过 staleMs(默认 180 秒)」判定过期，然后直接 unlink 抢占。
我写了个最小复现（把阈值调成 500ms 便于观察）：

```
A 进入 53899
B 进入 54701  <-- 与 A 同时持锁
A 退出 55901
```

**A 还在里面干活，B 就已经进去了。**

### 为什么会这样

```js
const st = fs.statSync(file);
stale = Date.now() - st.mtimeMs > staleMs;   // 只看文件多久没被改
if (stale) { fs.unlinkSync(file); continue; } // 直接抢
```

两个问题：
1. **没有心跳**：锁文件创建后 mtime 再也不更新（我 grep 过，全文件没有 utimes/touch）
2. **不检查持锁进程是否还活着**：文件里明明写了 pid，但判定时根本没用它

后果：任何持锁超过 3 分钟的任务，锁会被后来的任务抢走，两个任务同时控制同一个应用。
这正是这把锁存在的意义（防止并发误操作），结果它自己在长任务上失效。

目前用它的是 `multi-app` 和 `parallel-real-demo`，都是短任务，所以还没出事；
但 `app-matrix` 跑 420 秒，一旦有人给它加锁就立刻踩雷。

### 建议改法（两步）

**① 判过期前先看 pid 还活着没**：
```js
const holder = Number(fs.readFileSync(file, 'utf8').trim()) || 0;
let alive = false;
if (holder) { try { process.kill(holder, 0); alive = true; } catch {} }
stale = !alive || Date.now() - st.mtimeMs > staleMs;
```

**② 持锁期间心跳续期**：
```js
const hb = setInterval(() => { try { fs.utimesSync(file, new Date(), new Date()); } catch {} }, staleMs / 3);
hb.unref();
// finally 里 clearInterval(hb)
```

### 顺带

锁文件放在 `os.tmpdir()`（`/var/folders/...`），不同用户/不同 TMPDIR 会互不可见；
单机自用没问题，但如果以后多用户或 launchd 与终端 TMPDIR 不一致，锁会形同虚设。
建议挪到 `~/.desktop-agent/locks/`。
