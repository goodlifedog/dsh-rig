# 任务输出约定（写任务前先看这条）

> 验收与健康面板判定「这轮到底算不算失败」靠的是日志里的标记。标记用错，真失败会被吞掉、
> 环境问题会被报成 bug。三个标记各有严格语义，别混用。

## 三个标记

| 标记 | 含义 | 谁看它 |
| --- | --- | --- |
| `  PASS  xxx` / `  FAIL  xxx` | 单条断言的结果（任务自己的检查项） | 人看；`FAIL` 同时是**硬失败信号** |
| `环境跳过：<原因>` | 这次没验证，因为**环境不具备**（锁屏、应用没开、缺权限、用户正在用） | `run-classify` 判环境跳过，验收不计失败 |
| `❌ xxx` | 明确失败（脚本自己标红） | 硬失败，任何环境理由都不能豁免 |

另外 `结果: 存在失败项` 也是硬失败信号（有些任务用它做总结论）。

## 判定顺序（`core/run-classify.mjs`）

```
1. 日志里有 ❌ / FAIL / 未送达 / 存在失败项  →  真失败（不给任何环境理由豁免）
2. 否则命中 ENV_RULES（环境跳过、锁屏、用户在用、缺权限…）  →  环境跳过
3. 都没有，但退出码非 0  →  真失败
```

## 常见写错方式

```js
// ✗ 错：用 FAIL 表达环境问题——现在会被判成真失败（以前会假绿，改过了）
record('后台点击', false, { detail: 'FAIL: 屏幕已锁' });

// ✓ 对：环境问题显式声明，断言只表达“检查过了、通过/没通过”
if (await isScreenLocked()) { console.log('环境跳过：屏幕已锁，AX 不可用'); return; }
```

```js
// ✓ 断言失败就该是 FAIL（或 ❌），不要为了“好看”改成环境跳过
record('读回正文校验', ok, { detail: ok ? '内容一致' : '内容不一致' });
```

## 为什么要这么严

- 验收报告上的绿点必须是**真绿**：`HARD_FAIL` 优先级高于所有环境规则，就是为了堵住「一半跳过 + 一半失败」被整轮判 PASS
- 环境跳过是诚实标注，不是逃生舱：它只描述「没验证」，不描述「验证失败」

改这里的规则时，同步改 `core/run-classify.mjs`、`core/retry-policy.mjs`（复用同一份 ENV_RULES）与 `test/run-classify.test.mjs`。
