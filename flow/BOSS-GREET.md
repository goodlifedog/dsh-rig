# BOSS 投递：为什么「说已发送」却没送达，以及现在的可靠做法

> 2026-11-06 实测。结论先行：**不是配额问题，是弹窗从来没被关掉，导致后续每一条都在假发。**

## 1. 根因

旧版 `core/tasks/greet-inner.mjs` 点完「立即沟通」后，看到页面上有「已向BOSS发送消息」就记为「已发送」。
问题在于这句话**从第一次发送之后就一直在页面上了**。

弹窗在 AX（无障碍）树里长这样：

~~~text
318 container
  319 container
    320 标题 已向BOSS发送消息 Value: 3
    322 button Frame: x=954, y=445, w=24, h=24      <- 右上角 ×
    326 文本 您好，我是27 届应届生，会Java，…
    327 文本 如需修改打招呼内容，请在【消息通知-设置招呼语】页面修改
    328 container [留在此页](javascript:;) [继续沟通](javascript:;)   <- 两个按钮都不是独立节点
~~~

旧代码想点「留在此页」：

~~~js
function idxOf(text, needle) {           // 只认 "数字 link" 或 "数字 按钮"
  var m = /(\d+)\s+(link|按钮)/.exec(ls[i]); …
}
var stay = idxOf(s3, '留在此页');        // -> -1，永远 -1
if (stay >= 0) { … }                    // 所以这句从来没执行过
~~~

「留在此页」和「继续沟通」被渲染在同一个 `container` 的文本里，不是 `link` 也不是 `button`，
所以按角色取 index 必然失败 —— **弹窗一次都没被关过**。

于是形成这条链：

1. 第 1 条：点「立即沟通」→ 弹窗真的出现了 → 送达（这是唯一真的那条）。
2. 弹窗没关，遮罩层盖住整个页面。
3. 第 2 条起：点卡片、点「立即沟通」全被遮罩吃掉，什么也没发生。
4. 但脚本再读状态，`已向BOSS发送消息` 还在（来自第 1 条的旧弹窗）→ 判定「已发送」。
5. 消息列表当然没有任何新增 → 外面看到的就是「报已发送、实际没送」。

另一处让问题无法自证的是**详情没做真校验**：

~~~js
var key = j.title.split(' ')[0];       // "Java"、"java开发工程师"…
if (s2.indexOf(key) < 0) { … }         // 左侧列表里到处是 "Java"，永远为真
~~~

标题比对等于没比对，所以「点的是不是右侧那个岗位」从来没被确认过。

## 2. 现在的判定规则

| 事项 | 判定方式 | 说明 |
| --- | --- | --- |
| 详情是否切到目标岗位 | 「查看更多信息」链接里的 job_detail/<id> == 卡片 id | 不再用标题模糊匹配 |
| 是否已经联系过 | 详情面板按钮文案：立即沟通 / 继续沟通 | 继续沟通 就跳过，绝不点 |
| 平台是否受理了这次点击 | 弹窗**从无到有** | 点之前必须先确认弹窗不存在 |
| **是否真的送达** | **消息列表前后差集**，且能对上该岗位的招聘方 | 唯一验收标准 |
| 弹窗提示 | 只作参考 | **不作为送达依据** |

差集口径（`core/tasks/greet-verify.mjs#diffChat`）：
把会话项开头的「时间」剥掉后，取「姓名+公司+职位」作为 `who`；
`who` 新出现 = 新会话；`who` 相同但内容变了 = 已有会话里追加了消息。两者都算「有变化」。
再用内层从详情面板抓到的招聘方名字（抓不到就用公司名）去匹配这些变化项，
对得上才算这个岗位送达 —— 避免把别人的新消息记到这个岗位头上。

## 3. 现在的流程

~~~text
boss-greet.mjs（外层）
  1. 先读一次消息列表当基线；读不到就退出码 2，拒绝投递（没有验收手段不发）
  2. 调内层 greet-inner.mjs 处理一张卡片
       - 开场先清残留弹窗（清不掉就直接失败，不在被遮罩的页面上瞎点）
       - 点卡片 → 轮询到详情 job_detail id 等于目标 id
       - 按钮是「继续沟通」→ 返回「已联系过」（外层记为 skipped，永久跳过）
       - 确认没有弹窗 → 点「立即沟通」→ 轮询到弹窗出现
       - 立刻点弹窗右上角 × 关掉，并轮询确认它真的消失了
  3. 读消息列表，做差集 + 招聘方归属
       对上 → delivered，写进状态文件
       对不上 → failed（同岗位连续 2 次就不再碰）
  4. 连续 2 次没送达 → 停手，不盲目刷
~~~

每一步之间都有 1.2~4.5 秒随机停顿，点击全部走 accessibility 语义点击，
不移动系统指针、不激活 Chrome。

## 4. 用法

~~~bash
cd desktop-agent
export PATH=$HOME/.local/bin:$PATH
export OPEN_COMPUTER_USE_VISUAL_CURSOR=0   # 必须，否则屏幕上有假光标

GREET_LIMIT=2 node core/runner.mjs run boss-greet --timeout 600000
~~~

环境变量：

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| GREET_LIMIT | 2 | 本次要**确认送达**的条数 |
| GREET_DRY=1 | 关 | 只验证「点卡片 → 详情正确」，不点「立即沟通」，不消耗配额 |
| GREET_CARDS | 1 | 内层一轮最多翻几张卡片（外层是发一条核一条，正常别改） |
| TARGET_APP | Google Chrome | 被控应用 |
| OPEN_COMPUTER_USE_VISUAL_CURSOR | — | **必须为 0** |

状态文件 `reports/greet-state.json`：

~~~json
{
  "version": 2,
  "delivered": { "<jobId>": { "title": "...", "boss": "...", "company": "...", "evidence": "13:22 任先生易点云招聘专家 [送达] …" } },
  "skipped":   { "<jobId>": { "reason": "详情按钮=继续沟通" } },
  "failed":    { "<jobId>": { "count": 1, "reason": "消息列表无新增" } }
}
~~~

下一次运行会跳过 `delivered` + `skipped` + `failed` 满 2 次的岗位，不会重复打扰同一个人。
旧格式 `{ "done": [...] }` 会自动迁移成 `skipped`（宁可少发，不可重复发）。

每轮报告写 `reports/greet-<时间戳>.json`。

## 6. 已知限制 / 坑

- **必须在 `/web/geek/jobs` 列表页**。脚本会校验当前标签页 URL，不对就重试 8 次后报错退出。
  不会自己去切标签页，也不会新开标签页。
- **本机同时跑着多个 Chrome 实例时，ocu 有概率抓到别的 Chrome 窗口**（历史测试残留的
  离屏实例）。这会让脚本在错误的窗口上点击。现在的做法是：每次取状态都校验 URL 里包含
  `zhipin.com/web/geek/jobs`，不匹配就重试。
- **详情面板的招聘方姓名可能不渲染**（实测「志诚泰和」那个岗位 AX 里只有
  `文本 志诚泰和 · 人事专员`，没有姓名行）。所以归属匹配是「姓名优先，公司名兜底」。
- **核对要用专用离屏 Chrome**（`~/.desktop-agent/chrome-profile`，同一个 BOSS 账号），
  每次核对启动一次约 15~25 秒。该 profile 登录态失效时会明确报错，不会误判成「没送达」。
- **别在弹窗没关的情况下继续点**。现在的代码开场会强制清弹窗，清不掉直接失败退出。
- 只发第一条招呼：绝不追加第二条消息、不点「继续沟通」（那是进聊天页）、不碰简历和招呼语设置。

## 7. 相关文件

- `core/tasks/boss-greet.mjs` —— 外层：逐条发 + 用消息列表核对
- `core/tasks/greet-inner.mjs` —— 内层（在 ocu 运行时里跑）：点卡片 / 点立即沟通 / 关弹窗
- `core/tasks/greet-verify.mjs` —— 读消息列表 + 差集，唯一验收标准
