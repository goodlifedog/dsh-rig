# BOSS 直聘「打招呼」规则调研（求职者端）

> 调研日期：2026-11-06 · 纯公开资料调研，未登录、未操作浏览器、未改动任何账号数据
> 目的：解释 `boss-greet` 遇到的「弹窗说已发送，消息列表却没新增」现象，并给策略定界

## 0. 一句话结论

**BOSS 的每日主动沟通额度不是固定数字，而是按账号「权益」动态下发，官方明确不公开规则；超限后最常见的表现是「仍然弹出成功提示、但实际不再新建会话」——所以弹窗不能当送达凭证，只有 `/web/geek/chat` 会话列表的差集才算数。**

下面逐条给证据。每条都标了可信度：

- **A = 官方口径**（BOSS 自己的帮助页 / 官方客服回复）
- **B = 可核验的工程实现**（开源项目源码 + 真实 DOM 注释，能对上页面行为）
- **C = 用户实测帖**（多来源一致才采信）
- **D = 低可信**（SEO 农场 / AIGC 生成，只作为反例列出）

## 1. 每日沟通上限是多少？新号和老号是否不同？

### 结论

**没有公开的统一数字。**额度挂在「账号权益」上，同一个人换城市/换行业/换岗位/换供需关系都可能变；新号、未付费号额度低，付费后提升。

### 证据

**A｜官方客服回复（黑猫投诉，2020-08-05 投诉，客服 2020-08-06 回复）**

> 「城市不同，行业不同，企业不同，招聘岗位不同，市场供需不同，都会导致不同账号拥有不同的权益，该调整是为了给求职者带来更好体验以避免被高频打扰。」

同一投诉里，投诉人自述：

> 「将每日沟通人数被限制为 **3 人**……而且奇怪的是，我们花钱购买 VIP 之后，每日沟通数就可以达到 **60** 了。」

来源：<https://tousu.sina.com.cn/complaint/view/17350466649/>

**A｜官方客服回复（黑猫投诉，2021-07-14 投诉，客服 2021-07-15 回复）**

> 「您好，账号是有**基础权益**的，具体的权益可以在 **APP 我的--我的权益** 页面进行查看，**以页面提示为准**，如果沟通到上限后还需要解锁更多权益是需要付费升级的。」

来源：<https://tousu.sina.com.cn/complaint/view/17354016130>

这两条是我能拿到的**最接近官方**的说法，方向很明确：**额度是个性化的、以 App 内「我的权益」页面为准**，别去找一个固定数字。

**C｜新号额度低、付费额度高（豆瓣，2021-10-23，HR 视角）**

> 楼主：「boss直聘每天只能主动打 **3** 个招呼」
> 回复：「我朋友每天可以打 **100** 个招呼」「我 **200** 个……付费」

来源：<https://www.douban.com/group/topic/250671683/>

**C｜常见档位：100 左右（百度知道/百度经验，2021–2022）**

- 「一般是 100 人，个别付费用户有 150 人左右。」——<https://zhidao.baidu.com/question/1950080229987955028.html>
- 「上限都是 100 个，而且都是免费的。」——<https://jingyan.baidu.com/article/1974b28961e497b5b0f77429.html>

**B｜求职者端自动化工具文档：约 150/天**

开源项目 Get Jobs（9k+ star，Playwright 驱动 BOSS 求职者端）的配置文档写：

> 「**打招呼限额**：目前平台限制单日约 **150 次**。」
> 「Q5: Boss直聘提示打招呼失败？1. 检查今日是否已达到平台单日上限（目前平台限制约为 **150 次/天**）。2. 若未开启 AI，检查是否未填写默认打招呼语文本（`sayHi` 不能为空）。」

来源：<https://github.com/loks666/get_jobs/blob/main/docs/guide/config.md>、<https://github.com/loks666/get_jobs/blob/main/docs/guide/faq.md>

### 反例（D，别采信）

淘宝百科那类 SEO 农场有「每人每天最多 50 家」「一天 3 个招呼」等互相矛盾的说法，同一站点不同文章数字都不一样，还混着 AI 生成的文案。例：<https://bk.taobao.com/k/bosszhipin_663/72979d88afa3599698e811f6cdd2b692.html>

### 注意一个坑：很多数字是「招聘者端」的

网上大量「50/100/150/200」的帖子，主语是 **BOSS（招聘方）**，不是求职者。比如搜狗微信里一篇公众号写「非会员使用打招呼功能的上限是一天 40 次，用完需另外购买」——那是企业端。**招聘方额度 ≠ 求职者额度**，混用会得出错误结论。

### 对我们的意义

- 不要在任何地方硬编码「每天 N 条」这个常量。用**实测送达数**当额度。
- 想知道自己的真实额度，唯一可靠办法是打开 App「我的 → 我的权益」看（需要人工看一次，我们不自动化）。
- 我们账号 2026-11-06 的表现是「3 条之后不再新增会话」（见 `flow/BOSS-QUOTA.md`）。这个数字和网上多处「基础档 3 条」一致，**但要注意：所有「3 条」的来源都是招聘者端账号**，求职者端是否同样是 3 条档，我没找到直接证据。所以这只是**类比推断，不是已证实结论**——它比「150 条用完了」更可能，但两者都不能算定论。

## 2. 超限后界面表现是什么？会「仍提示成功但不发送」吗？

### 结论

**会。**超限后 UI 层仍会走完「已向BOSS发送消息」的提示，但服务端不再创建会话——这正是我们遇到的现象。这一点由三方面独立佐证：

### 证据

**A/C｜官方提示语（百度知道，用户转述实际弹窗）**

> 「100个，再沟通就会提示：**您今日在非火爆职位中的总沟通人数已达上限，请明日再试**」

来源：<https://zhidao.baidu.com/question/1950080229987955028.html>
（注：这条提示语措辞偏招聘者端「总沟通人数」，但「达上限 / 请明日再试」的形态是通用的。）

**B｜自动化工具把「打招呼失败」直接归因于上限**（见上，Get Jobs FAQ Q5）——说明在真实页面里，超限是一条**失败路径**，工具需要专门排查。

**D（旁证，慎用）｜第三方插件故障分析**

> 「虽然显示『投递成功』，但实际消息并未发送」
> 归因：WebSocket 消息同步延迟 + token 获取方式变更。

来源：<https://blog.csdn.net/gitblog_07079/article/details/148010342>
**这篇文章文末自述「部分内容由 AI 辅助生成」，不是硬证据**，但它描述的「显示成功 ≠ 真发送」和我们实测一致。

**C｜我们自己的实测（最硬）**

`flow/BOSS-QUOTA.md`：11:20 / 11:58 / 12:01 三条送达；之后 8 个岗位「弹窗提示已发，消息列表无新增」。

### 关键推论

「已向BOSS发送消息」弹窗是**前端结果通知**，不是服务端回执。超限、岗位已停招、或被风控降权时，这个弹窗照样弹。

## 3.「已向BOSS发送消息」提示代表真的发出吗？「留在此页」和「继续沟通」分别是什么语义？

### 结论

- 弹窗本身 = **「招呼已提交」的 UI 通知**，不是送达凭证。
- **两个按钮都只是导航选择，不是「确认发送 / 取消发送」**：
  - **留在此页** = 留在当前职位页/列表，继续挑岗位；
  - **继续沟通** = 跳到聊天页（会话已建立）。
- 弹窗出现 ≠ 会话已建立。真正凭证是 `/web/geek/chat` 里出现新会话。

### 证据（B，最强）

Get Jobs 的 `BossChatNavigator.java`，注释标注「2026-10-21 从真实 Boss 页面 DOM 采集确认」：

```java
// 2026-10-21 从真实 Boss 页面 DOM 采集确认：两个沟通入口都可能出现此通知框。
static final String GREET_CONFIRM = ".greet-boss-dialog:visible .greet-boss-footer a.sure-btn";
// 先定位可见的"留在此页"，再取同时包含两个按钮的最近共同祖先。
static final String STAY = ":text-is('留在此页'):visible";
```

并对「已向BOSS发送消息」给出了明确判断：

> 「**「已向BOSS发送消息」也是首次打招呼的结果通知**，不能据此改成旧会话。」

来源：<https://github.com/loks666/get_jobs/blob/main/src/main/java/com/getjobs/worker/boss/BossChatNavigator.java>

也就是说：**这个弹窗是「首次打招呼」的结果通知**，两个按钮（`a.sure-btn`=继续沟通、`留在此页`）纯粹决定接下来去哪一页。

同一个仓库的 `Boss.java` 还揭示了一个对我们很有用的细节：

> 「Boss 第一次『立即沟通』有时只打开**简化打招呼层**，发完文字后该层不会提供图片按钮。此时关闭简化层并重新点击『继续沟通』，等待完整聊天 DOM。」

来源：<https://github.com/loks666/get_jobs/blob/main/src/main/java/com/getjobs/worker/boss/Boss.java>（约 1304 行）

所以完整链路是：**立即沟通 → 简化打招呼层 → 输入并发送 → 弹「已向BOSS发送消息」→ 继续沟通 进完整聊天页**。

### 对我们 bug 的直接启示

1. 只要弹窗出现就记「成功」是**错的**——弹窗在超限时也会出现。
2. 点「继续沟通」只是进聊天页，**不会补发任何消息**。指望「点了继续沟通才算真发」是误判；它和「留在此页」的差别只在跳转。
3. 真正要验的是会话列表（我们已有 `greet-verify.mjs`）。

## 4. 对方未回复前，能否追加消息？

### 结论

**能。**已建立会话后可以继续发消息；岗位卡片/详情按钮的文案会从「立即沟通」变成「继续沟通」，这个文案本身就是「已联系过、可继续聊」的标记。

但**官方没有公开「未回复最多能追几条」的规则**——这条查不到官方说明。

### 证据

**B｜按钮文案即状态机**

`Boss.java` 用按钮文案判断是否已联系过：

```java
Locator chatBtn = detailPage.locator("a.btn-startchat, a.op-btn-chat");
String buttonText = chatBtn.first().textContent();
if (buttonText.contains("继续沟通") && !allowRepeatChat) {
    log.info("已关闭重复沟通，跳过已沟通Boss ...");
}
```

**B｜该工具有「重复沟通」功能，能对未回复的会话追加消息**

`changelog`：「Boss 重复沟通支持自定义随机消息……开启重复沟通后，遇到「继续沟通」随机发送一条非空行，不调用首次打招呼的 AI 流程。」

来源：<https://github.com/loks666/get_jobs/blob/main/docs/guide/changelog.md>

说明**技术上可以追加**，社区也在这么做。

### 但要注意

- 追加消息大概率**同样计入频控**（它就是一个新的发送动作）。该工具对重复沟通默认是**关闭**的，需要用户显式打开——这个默认值本身说明维护者认为频繁追加有风险。
- 查到的一些帖子提到「未回复只能发一条」的说法，**我没找到任何官方或可靠来源支撑**，不采信。

## 5. 哪些行为会触发风控？有官方说明吗？

### 结论

**官方没有公开任何量化风控规则。**能查到的是事实性的触发结果和工程界的应对经验。

### 官方侧（A）

BOSS 官网公开的规则页只有这几处，**都不涉及沟通频控数字**：

- 使用帮助 <https://www.zhipin.com/web/common/protocol/use-help.html>（只有换手机号、隐藏简历、屏蔽公司等）
- 防骗指南 <https://www.zhipin.com/web/common/protocol/cheat-guide.html>
- 协议与规则 <https://about.zhipin.com/agreement>（SPA，正文需登录渲染，本次未取到）
- 首页页脚另有「职位发布规则」

所以「多少分钟内发多少条会被封」这类规则，**官方查不到，属于黑盒。**

### 实际触发后的表现（B，可核验）

Get Jobs 源码里明确写了风控会把人弹到验证页，并且列出了真实 URL：

```java
/**
 * 判断是不是 Boss 的安全验证页。
 * 实测密集遍历后会被弹到 /web/passport/zp/verify.html（极验滑块，
 * 页面上是 div.geetest_success_correct 那一套）...
 */
private static boolean isSecurityVerifyUrl(String url) {
    return url.contains("/web/user/safe/verify-slider")
        || url.contains("/web/passport/zp/verify")
        || url.contains("/web/passport/zp/security")
        || url.contains("security-check");
}
```

来源：<https://github.com/loks666/get_jobs/blob/main/src/main/java/com/getjobs/worker/boss/Boss.java>

**所以风控的第一表现是：跳到极验滑块验证页**（`/web/passport/zp/verify.html`），不是弹一个「你违规了」。

### 触发条件（C，但证据链完整）

GitHub Issue #303「boss被风控了」：

> 用户：「今天刚刚运行大概 **5 分钟**然后就被风控了……**风控一天**，是不是 boss 可以识别了？」
> 作者（loks666）回复：「**是你投的太快了**，自己反思吧」

来源：<https://github.com/loks666/get_jobs/issues/303>

同一作者在代码里给出的对策，也是从踩坑里总结的：

> 「正常模式在 [wait_time/2, wait_time] 之间随机，**避免固定节奏本身成为特征**。」
> 「停顿期间可能已经被弹到安全验证页，发现了就停下来等人工过验证，而不是继续闷头点下去。」

### 归纳出的高风险行为

1. **速度**：连续快速点「立即沟通」，几分钟内就可能触发（issue #303 是 5 分钟）。
2. **固定节奏**：等间隔机器人式操作，比随机间隔更容易被识别（作者原话）。
3. **批量/密集遍历**：滚动加载几百个岗位 + 逐个点，会被弹验证页。
4. **弹到验证页后继续硬点**：会让后续全部失败，甚至延长限制。
5. 关于「非本人设备 / 异地登录」触发风控——**官方无说明，我也没找到可靠实测帖，查不到。**

**注意**：以上是社区/工程经验，不是官方规则；BOSS 可以随时调整。

## 6. 对我们这个 bug 的解释（结合 `BOSS-QUOTA.md` 的实测）

按可能性排序：

1. **额度用尽（最可能）**。账号权益档位低（可能是 3 条档），3 条之后服务端不再建新会话，但前端照样弹「已向BOSS发送消息」。与实测完全吻合。
2. **右侧详情没切换，点到了同一个/错误的按钮**。这是 task-9 正在查的方向；如果是这个原因，表现也是「提示成功但列表无新增」。
3. **岗位已停招/已下线**。BOSS 上大量岗位挂着但实际不招（搜狐那篇产品分析专门吐槽过这点：关闭职位需 BOSS 手动操作，导致职位池里有大量僵尸岗位）。给僵尸岗位发招呼，会话可能不建立。来源：<https://news.sohu.com/a/726187257_114819>
4. **列表未刷新/WebSocket 延迟**。概率最低——我们的 `greet-verify` 是重新读页面，且有 3 条成功案例证明读法是通的。

**结论：1 和 2 都无法用「弹窗」区分，只能用会话列表差集区分。**任务 9 把差集当唯一验收标准是对的，应当坚持。

## 7. 对策略的影响（可执行）

1. **唯一验收 = 会话列表差集。**任何「弹窗成功」「按钮消失」「日志显示已发」都不算数。`flow/BOSS-QUOTA.md` 已定这条，本报告从规则侧确认它是对的。
2. **别硬编码每日上限。**当作未知量：跑到连续 N 次（建议 N=2）差集无新增就停，判定「本轮额度用尽」，记录时间，第二天再看。
3. **节奏要慢且随机。**单条之间 30–120 秒随机；不要固定 5 秒。一次运行不超过 10–15 分钟（issue #303 的 5 分钟翻车是下限参考）。
4. **检测验证页并立刻停。**URL 命中 `/web/passport/zp/verify`、`/web/user/safe/verify-slider`、`security-check` 就中止任务、报给用户，**绝不尝试自动过滑块**。
5. **点之前校验右侧详情标题与目标岗位一致**（task-9 已在做）。这是排除「原因 2」的唯一手段。
6. **不要用「继续沟通」当补发手段。**它只是跳转，不补发；真要追加消息得重新输入+发送，且要计入额度与风控风险，默认关闭。
7. **不要指望付费解决。**付费升权益是账号持有人的决定，属于产品边界外的事，agent 不应触碰。
